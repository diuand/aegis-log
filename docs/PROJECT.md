# aegis-log: project definition

## 1. Definition and scope

**What it is.** A small log-enrichment service for a security team. It
receives log events, normalizes them, tags events from known-bad IPs using a
local threat-intel feed, applies detection rules and keeps the results
searchable. It stands in for the ingestion and enrichment stage of a SIEM
pipeline (Logstash, OpenSearch and MISP in the syllabus and the course demo),
cut down to what runs on an 8 GB laptop.

**Why it exists.** It is the subject of a risk and damage management
exercise. The scope comes from the risk register (`RISK-REGISTER.xlsx`,
written before any code in PR #1). Every component exists either because the
service needs it or because a register row needs something real to protect
and test. The course template was not available, so the workbook is
generated by `scripts/build_register.py` with the same structure (Read me,
Register, Scales, Heat map), which also makes every register change a
readable diff.

**In scope.** The Flask service and its six endpoints; the ten seeded bugs
and their fixes; repository, CI and AI-agent guardrails; evidence that each
control works.

**Out of scope (deliberately).** Production deployment, real intel
platforms, dashboards, containers, signing. See section 8.

in (REST `attributes/restSearch`, key from `AEGIS_INTEL_API_KEY`); it is
never enabled by default and never called in tests. Shodan would be a
second provider (host context for source IPs: open ports, banners); it is
documented here only.

## 4. How the seeded bugs are kept honest

- **Regression tests first.** Each bug has tests marked `@pytest.mark.seeded_bug("B-xx")` that drive the real exploit path with a harmless marker (a canary function for YAML, a marker file for traversal, a fake token for logs).
- **`tests/bug_ledger.py` plus strict xfail.** While an ID is listed, its tests run as `xfail(strict=True)`: they *must* fail. The suite is green on the vulnerable baseline without hiding anything, and a test that passed early would turn it red. Each fix PR deletes exactly one ID, so the diff shows the bug closing.
- **Red and green evidence.** `make evidence-red` runs the seeded tests with xfail switched off: 32 failures on `baseline-vulnerable` (`docs/evidence/baseline-red.txt`). `make evidence-green` runs the same 32 on `main`: 32 passes (`docs/evidence/final-green.txt`).
- **Tracked exceptions.** The scanners went live in phase 3 while B-01 to B-08 were still open on purpose. Their findings were recorded as exceptions tied to a bug ID (`# tracked: B-02 # nosec B608`, `.pip-audit-ignore` lines). `tests/test_tracked_exceptions.py` fails if an exception names a closed bug, so none outlives its bug. On `main` there are none.

## 5. GitHub route 4: what is enforced and what is only detected

Private repository on GitHub Free: **branch protection and rulesets are not
available**, and CODEOWNERS review cannot be made required.

| Goal | Free-plan equivalent here | Enforced? |
|---|---|---|
| No direct commits to `main` | `no-commit-to-branch` pre-commit hook | locally; a human can skip hooks |
| No direct or force pushes | `protect-main-push` pre-push hook; agent `PreToolUse` guard and deny rules | locally; a human can skip hooks, the agent cannot |
| Every change via a merged PR | `governance.yml` checks main's first-parent history against merged PRs after every push (root commit exempt) | **detective**: red run plus e-mail, not a block |
| Required status checks | CI on every PR; "merge only when green" is a written rule | by discipline |
| Owner review of sensitive paths | CODEOWNERS auto-requests the owner | not required |
| Secret scanning / push protection | gitleaks in pre-commit and CI | locally and in CI (detective after push) |

**If the plan changes** (public repository, GitHub Pro, or the ULBS
organization): add a ruleset on `main` with *require a pull request* (one
approval, code-owner review), *require status checks* (`ruff + pytest +
import check`, `bandit`, `pip-audit`, `gitleaks`, `zizmor`), *block force
pushes* and *restrict deletions*, and turn on secret-scanning push
protection. The governance workflow then becomes a second line instead of
the only one, and R-10's likelihood drops from 3 to 2.

## 6. AI workflow

- **`CLAUDE.md`**: role, voice, banned-patterns table (each row tied to a risk and bug), stack conventions, default commands. It imports only `memory/MEMORY.md`.
- **`memory/`**: one file per real correction made while building: PyYAML reading `on:` as `True`, bandit parsing words after `nosec`, evidence leaking the fake key and home paths, a negative sample that matched its rule, make on Windows; plus the quarantined poisoned note kept as a record of B-10.
- **`skills/fix-seeded-bug`**: branch, reproduce, test first, fix, close in the ledger, `make check`, bug report, register, review, PR.
- **`skills/review-pr`** (+ `review.py`): run locally before every PR. A mechanical pass flags banned patterns in added lines, sensitive paths, commits without risk IDs and code changed without tests; a judgement pass answers nine questions. The output goes under "Agent review" in the PR. Its first real run produced false positives on the guard's own deny lists, which were fixed before that PR was opened.
- **Enforcement**: `.claude/settings.json` deny rules and the `PreToolUse` hook (`.claude/hooks/guard.py`). This is what actually stops the agent; the prose only explains it (see B-10, "why prose alone is not a control").

### PR review without an API key (honest limits)

There is **no automated reviewer gate**. No model API key was available, and
Copilot code review is not part of Copilot Free. What exists instead is an
**agent-assisted** review: `skills/review-pr` runs locally before each PR
and writes its findings into the PR description, and the PR template's
checklist is mandatory by convention. Nothing in GitHub stops a PR from
being merged without either. That is why R-10's residual stays at 3 x 4 = 12.

**How an Actions-based reviewer would be wired later:**
1. Store the model API key as an encrypted repository secret (for example `REVIEW_API_KEY`). Never commit it and never print it.
2. Add `.github/workflows/ai-review.yml` on `pull_request` (never `pull_request_target`), with `permissions: contents: read` at the top and `pull-requests: write` only on the review job, every action SHA-pinned.
3. Fork PRs receive no secrets on `pull_request`, so the job skips them (`if: github.event.pull_request.head.repo.full_name == github.repository`) instead of failing.
4. The job sends the diff plus `CLAUDE.md`'s banned patterns to the model and posts a review comment. On a plan with rulesets its status becomes a required check.

**Effect on the register:** R-10 likelihood 3 -> 2 (every PR gets a second
pass that cannot be forgotten), residual 12 -> 8; with branch protection as
well, likelihood -> 1. The new secret adds a small R-01 exposure (a key in
CI), contained by the fork-PR rule and minimal permissions.

## 8. Limits: what was deliberately not built

| Not built | Why | What stands in |
|---|---|---|
| OpenSearch, Logstash, Grafana, Prometheus | do not fit next to a browser and an IDE in 8 GB | SQLite, a Flask normalizer, a text report |
| MISP, Shodan | not installed; no traffic to other hosts allowed | local JSON feed behind `IntelProvider`; MISP stub; Shodan documented |
| Docker image, Hadolint, Trivy | no Dockerfile (not required; Docker not needed locally) | pip-audit for dependencies |
| Syft SBOM, Cosign signing | nothing is published or released | exact pins; could be added to CI later |
| Semgrep | optional heavy scanner | bandit, ruff and regression tests |
| SOPS/age for secrets | optional in the spec; no real secret exists | git-ignored `.env`, gitleaks |
| Rate limiting, TLS, per-client keys | out of scope for a loopback lab service | one random API key, `127.0.0.1` bind (R-04, R-05 residuals) |
| Branch protection, required reviews | not on GitHub Free for private repositories | section 5 |
| Automated AI PR reviewer | no API key | section 6 |

## 9. What the owner must do by hand

- Merge only when CI is green and the checklist is complete; nothing on the server enforces it (section 5).
- Run `make hooks` once per clone (git hooks are not cloned). It needs `gitleaks` on PATH.
- If the repository moves to a plan with rulesets, apply the ruleset in section 5.
- If an AI reviewer is wanted, add the key as a repository secret and the workflow in section 6.
